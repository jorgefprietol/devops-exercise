OPERACIÓN DEL DESPLIEGUE

GitHub Actions compila, prueba y publica la imagen. La etapa de despliegue
registra una solicitud en GitHub Deployments. El agente local la consulta
mediante HTTPS, comprueba origen, etapas previas y versión, aplica Kubernetes
y devuelve el resultado. Excluye las solicitudes de cambios y conserva los
secretos y el acceso al cluster dentro del equipo.

RED
Internet -> HTTPS público -> túnel saliente -> 127.0.0.1:9443
-> NodePort 30443 -> Kong -> Servicio de la API -> Redis.

Cloudflare verifica el certificado del origen mediante .local/tls.crt.
El cliente utiliza TLS público válido y debe presentar API Key y JWT.

INICIAR O REANUDAR
Abrir Docker Desktop y ejecutar desde la raíz del repositorio:
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Start-Lab.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Test-PublicApi.ps1

Desde otra carpeta debe indicarse la ruta absoluta. Los scripts cambian a la
raíz del proyecto después de que PowerShell haya encontrado el archivo.
La opción Bypass se limita al proceso de ese comando.
Start-Lab.ps1 detecta Python con py o PATH y admite -PythonExe con su ruta.
Se requiere Python >=3.10. El agente usa la biblioteca estándar de Python.

Cada reinicio del túnel obtiene una URL nueva, guardada en .local/public_urls.json.
El agente atiende solicitudes durante ocho horas. Al terminar esa sesión,
Start-Lab.ps1 permite iniciar otra. Sin agente no hay nuevos despliegues;
una aplicación ya desplegada puede continuar mientras Docker y el túnel estén activos.

INSTALACIÓN EN OTRO EQUIPO
Requiere Docker, .NET 8, Python, kubectl, gh autenticado, kind y cloudflared.
bootstrap_addons.py requiere PyYAML y cryptography; instalarlos en un entorno
virtual dedicado. A continuación:
py -3 scripts/init_local.py
kind create cluster --config infra/kind.yaml --kubeconfig .local/kubeconfig
py -3 scripts/bootstrap_addons.py

Situar cloudflared.exe en .local/bin y ejecutar Start-Lab.ps1.
Comprobar que la subred de Docker no se solape con otras redes.

ENTORNOS
El despliegue público configurado corresponde a production.
development y staging usan otros namespaces y NodePorts: 30445 y 30444.
Para habilitarlos hay que exponer sus servicios, crear sus túneles y registrar
las URL en .local/public_urls.json. production es el nombre del entorno del
ejercicio; el alojamiento continúa siendo un laboratorio local.

DIAGNÓSTICO
400 con aviso de HTTPS: se utilizó http:// en un puerto que espera https://.
405 al abrir /DevOps: el navegador envía GET, pero el contrato exige POST.
401/403: comprobar credenciales y vigencia. 409: emitir un JWT nuevo.
502/503: revisar túnel, Kong, API y Redis.
Archivo .ps1 inexistente: usar una ruta absoluta o la raíz del repositorio.

Kong utiliza dos procesos para ajustarse al límite de memoria. La distribución
considera taints y revisiones para permitir escalado y mantener réplicas en
ambos trabajadores. La prueba de HPA usa carga sintética de CPU y no mide
la capacidad máxima de tráfico HTTP.

REGISTROS
.local/agent.log y .local/agent-error.log: despliegue local.
.local/tunnel.log: conexión pública. GitHub Actions: etapas y artefactos.
