OPERACIÓN DEL DESPLIEGUE

GitHub Actions compila, prueba y publica la imagen. La etapa de despliegue
registra una solicitud en GitHub Deployments. El agente local la consulta
mediante HTTPS, comprueba origen, etapas previas y versión, aplica Kubernetes
y devuelve el resultado. Excluye las solicitudes de cambios y conserva los
secretos y el acceso al cluster dentro del equipo.

RED
Internet -> HTTPS público -> túnel saliente -> 127.0.0.1:9443
-> NodePort 30443 -> Kong -> Servicio de la API -> Redis.

Cloudflare verifica el certificado del origen mediante .local/tls.crt.
El cliente utiliza TLS público válido y debe presentar API Key y JWT.

INICIAR O REANUDAR
La demostración rápida para evaluadores usa scripts/demo.py (ver README.txt).
Esta sección opera el laboratorio Kubernetes del propietario del repositorio.
Abrir Docker Desktop y ejecutar desde la raíz del repositorio:
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Start-Lab.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Test-PublicApi.ps1

Desde otra carpeta debe indicarse la ruta absoluta. Los scripts cambian a la
raíz del proyecto después de que PowerShell haya encontrado el archivo.
La opción Bypass se limita al proceso de ese comando.
Start-Lab.ps1 detecta Python con py o PATH y admite -PythonExe con su ruta.
Se requiere Python >=3.10. El agente usa la biblioteca estándar de Python.

Cada reinicio del túnel obtiene una URL nueva, guardada en .local/public_urls.json.
El agente atiende solicitudes durante ocho horas. Al terminar esa sesión,
Start-Lab.ps1 permite iniciar otra. Sin agente no hay nuevos despliegues;
una aplicación ya desplegada puede continuar mientras Docker y el túnel estén activos.

INSTALACIÓN EN OTRO EQUIPO
Requiere Docker, .NET 8, Python, kubectl, gh autenticado, kind y cloudflared.
bootstrap_addons.py requiere PyYAML y cryptography; instalarlos en un entorno
virtual dedicado. A continuación:
py -3 scripts/init_local.py
kind create cluster --config infra/kind.yaml --kubeconfig .local/kubeconfig --image kindest/node:v1.34.11@sha256:44e222ee2132dab25ff87301682f89eb82c7880ea3a1bf543bfe9708fd08d67d
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install PyYAML cryptography
.\.venv\Scripts\python.exe scripts/bootstrap_addons.py

En Windows instalar: winget install --id Cloudflare.cloudflared -e --source winget
Start-Lab.ps1 lo detecta en PATH o Program Files y admite .local/bin como respaldo.
Si ya existe un túnel del laboratorio, lo conserva para mantener su URL.
Ejecutar Start-Lab.ps1.
Comprobar que la subred de Docker no se solape con otras redes.

ENTORNOS
production: namespace devops-production, HTTPS local 9443, NodePort 30443.
staging: namespace devops-staging, HTTPS local 9444, NodePort 30444.
development: namespace devops-development, HTTPS local 9445, NodePort 30445.
Cada uno tiene Redis, volumen, JWT_SECRET y REDIS_PASSWORD propios.
La API Key fija del ejercicio es compartida por especificación.

En otro equipo, después de bootstrap_addons.py, seleccionar un digest publicado:
$imagen = 'ghcr.io/jorgefprietol/devops-exercise@sha256:REEMPLAZAR_POR_DIGEST'
py -3 scripts/prepare_environment.py production --image $imagen
py -3 scripts/prepare_environment.py staging --image $imagen
py -3 scripts/prepare_environment.py development --image $imagen
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Start-AllEnvironments.ps1

La preparación es idempotente: conserva los secretos y los volúmenes existentes.
Producción usa .env. Los demás usan .local/environments/<entorno>.env.
Los puertos 9444/9445 se conectan al servicio Kong mediante port-forward TLS,
limitado a loopback. El supervisor reconecta si el pod seleccionado termina.
Los tres túneles se conservan mientras sus procesos sigan activos.

Comprobar cada URL pública y credenciales:
py -3 scripts/test_environment.py production
py -3 scripts/test_environment.py staging
py -3 scripts/test_environment.py development
Agregar --local para comprobar el acceso HTTPS local en Kubernetes.

VERSIONES Y EJECUCIÓN BAJO DEMANDA
Push a master: production; push a develop: development; etiqueta v*: staging.
La imagen se aplica por digest inmutable, sin depender de una etiqueta latest.
GitHub -> Actions -> Integración y despliegue DevOps -> Run workflow.
Seleccionar una etiqueta publicada, un entorno y version vX.Y.Z.
Desde CLI, ejemplo de versión publicada hacia staging:
gh workflow run ci-cd.yml --ref v1.0.0 -f environment=staging -f version=v1.0.0
Si se selecciona master, el destino es production aunque se pida otro entorno:
gh workflow run ci-cd.yml --ref master -f environment=staging -f version=v1.0.0
Esta regla mantiene la exigencia del enunciado para master.
No editar ni mover etiquetas existentes. Una modificación crea otra versión.
Consultar evidencias y enlaces reales en evidence/cierre-entornos.json.

DIAGNÓSTICO
400 con aviso de HTTPS: se utilizó http:// en un puerto que espera https://.
405 al abrir /DevOps: el navegador envía GET, pero el contrato exige POST.
401/403: comprobar credenciales y vigencia. 409: emitir un JWT nuevo.
502/503: revisar túnel, Kong, API y Redis.
Archivo .ps1 inexistente: usar una ruta absoluta o la raíz del repositorio.

Kong utiliza dos procesos para ajustarse al límite de memoria. La distribución
considera taints y revisiones para permitir escalado y mantener réplicas en
ambos trabajadores. La prueba de HPA usa carga sintética de CPU y no mide
la capacidad máxima de tráfico HTTP.

REGISTROS
