OPERACIÓN DEL DESPLIEGUE

GitHub Actions compila, prueba y publica la imagen por digest. El despliegue
registra una solicitud en GitHub Deployments. El agente del propietario
comprueba origen, versión y etapas previas, aplica Kubernetes y comunica
el resultado. Las solicitudes canceladas y los pull requests no se despliegan.

La verificación usa kubectl port-forward autenticado, limitado a 127.0.0.1,
con un puerto temporal que se cierra al terminar. Comprueba HTTPS, contrato,
autenticación, JWT repetidos y concurrencia, dos réplicas de API y Kong en dos
nodos diferentes y HPA con métricas disponibles. No requiere URL pública,
Pinggy ni Cloudflare. El PC, Docker y el agente sí deben estar encendidos.

INSTALACIÓN COMPLETA EN OTRO EQUIPO
Docker Linux y Python 3.10 o posterior; Internet para la primera descarga.
Desde la carpeta del repositorio:
py -3 scripts/lab.py --all-environments

En Linux/macOS sustituye py -3 por python3. El script prepara kind, dos
trabajadores, Calico, Metrics Server, TLS y tres namespaces con secretos
independientes. Usa la imagen de infra/release-image.txt; --image selecciona
otra imagen por digest. El laboratorio se ha probado con 16 GB para Docker.
No requiere cuenta cloud ni SDK .NET. No crea servidores físicos independientes.

Para la demostración Docker más ligera:
py -3 scripts/demo.py

Compose tiene dos instancias detrás de Kong. El laboratorio Kubernetes añade
dos nodos trabajadores y HPA. La instalación local no requiere acceso a la
cuenta GitHub del propietario y no opera automáticamente su pipeline.

AGENTE DEL PROPIETARIO
Con gh autenticado y permisos sobre Deployments del repositorio:
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Start-Lab.ps1

Para mantener el acceso local a los tres entornos en Windows:
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Start-AllEnvironments.ps1

Los accesos son production 9443, staging 9444 y development 9445.
Start-AllEnvironments inicia supervisores de port-forward para staging y
development. En Linux/macOS se puede mantener abierto un port-forward:
kubectl --kubeconfig .local/kubeconfig -n devops-staging port-forward service/kong 9444:443 --address=127.0.0.1

La verificación conjunta abre y cierra sus propios puertos:
py -3 scripts/verify_environments.py

Publicar una copia del repositorio no concede acceso al cluster del propietario.
Para operar un fork es necesario configurar su identidad y el nombre del
repositorio/propietario en local_deploy_agent.py, con permisos apropiados.

VERSIONES Y EJECUCIÓN BAJO DEMANDA
Push a master -> production. Push a develop -> development.
Etiqueta vX.Y.Z -> staging. Pull request -> compilación y pruebas, sin desplegar.
Actions -> Integración y despliegue DevOps -> Run workflow permite elegir
entorno y una etiqueta existente. La imagen se aplica por digest inmutable.

Ejemplo para una versión publicada:
gh workflow run ci-cd.yml --ref v1.0.2 -f environment=staging -f version=v1.0.2

Al seleccionar master el destino siempre es production, aunque se solicite
otro entorno. Producción solo acepta una versión perteneciente a master.
Para revertir, selecciona una etiqueta anterior compatible; esto no revierte
datos ni secretos. Las modificaciones nuevas deben crear otra etiqueta.

NUBE
scripts/deploy_cluster.py despliega en un cluster existente usando un contexto
explícito. NUBE.md documenta EKS/AKS, perfiles, almacenamiento, TLS y permisos.
La aplicación es portable; el repositorio no crea una cuenta ni un cluster cloud.
La identidad y la conexión automática del pipeline a esa cuenta son configuración
del destino y no se han validado en AWS/Azure en este laboratorio.

PUBLICACIÓN OPCIONAL
Solo si se necesita una demostración desde Internet:
py -3 scripts/demo.py --public
py -3 scripts/public_tunnel.py production --renew

También se puede usar Start-Lab.ps1 -Public. Pinggy gratuito utiliza sesiones
de hasta 60 minutos y la URL cambia al renovar. El túnel no interviene en
la aprobación del pipeline. La prueba pública adicional es:
py -3 scripts/test_environment.py production

TRACE devuelve 405 ERROR. HEAD devuelve 405 sin cuerpo por el protocolo HTTP.
Una URL antigua de Cloudflare puede interceptar TRACE antes de llegar a Kong.

REGISTROS Y DIAGNÓSTICO
.local/agent.log y .local/agent-error.log: agente.
.local/releases/<commit>/verificacion-<entorno>.json: comprobación del despliegue.
GitHub Actions: etapas, artefactos, pruebas y cobertura.
400 al usar http:// en un puerto HTTPS: cambia a https://.
405 en navegador: envía GET; la petición válida requiere POST.
401/403: revisa credenciales. 409: genera un JWT nuevo.
Ruta scripts/demo.py inexistente: entra en la carpeta del repositorio.
HPA sin métricas: revisa Metrics Server y los recursos solicitados por los pods.
